# SAC-PAD — Project Specification

**SAC-PAD** = *Special Administration Cadre – Political Acceleration & Development*

This document captures the product requirements derived from the Eraser wireframe export, plus the architectural decisions needed to start building. It is written to be handed to an AI planning/build agent (bemad) to generate a PRD, architecture doc, and implementation epics/stories.

---

## 1. Overview

SAC-PAD is a political cadre / constituency management platform used by a political organization to track grassroots issues, party cadre activity, ground-level field reports, PR/media coverage, social media presence, voter lists, and a red/amber/green ("RAG") risk/opportunity mapping of constituencies — all rolled up into dashboards and exportable reports.

The platform is used by a **hierarchical chain of people within one Politician's organization** (an Org Admin who places state-level, district-level, taluka-level, and karyakarta-level users anywhere in the tree), plus an **external Dreamline User** role with narrower access. Each person should only see the data relevant to themselves and their branch of the hierarchy, each organization's **Org Admin(s)** see everything within their own organization, and a platform-wide **Admin** — a separate kind of account entirely, not part of any organization's user list, and able to host rival politicians from competing parties side by side without either ever seeing the other's data — sees across every organization.

### Primary users
- **Admin** — the platform operator (effectively the development team). **Modeled as a completely separate account type (`Admin`), not a row in the `users` table or a role in the `roles` catalog** — see §3.0. Not tied to any single politician/organization — can see and manage every organization on the platform (or a scoped subset, for `ops`-tier Admin), create organizations and their Org Admin account(s), **is the only account type that can define new roles and their module/capability scope** for the `User` side of the system, and manages platform-wide settings and shared reference data (e.g. State/Loksabha/Assembly/Village geography — §8, political Parties — §3.1b, Kitchen Cabinet ticket categories — §6.1, PR catalogs — §6.4) as well as each organization's own `Politician`/opponent roster (§6.3a). Logs in through a separate route into a separate Platform Console, not the organization dashboard (§5a).
- **Org Admin** — owns one organization (one Politician's operation/campaign). Full read/write/update (RWU) access to all data and all users *within their own organization only* — cannot see other politicians' organizations. **An organization can have more than one Org Admin** (e.g. the Politician plus a chief of staff), each with the same full org-wide access.
- **User** — a person in the cadre hierarchy under a given organization (e.g. state head, district head, karyakarta). Sees data for their own branch of the hierarchy ("Customer End" in the wireframe annotations), always within their own organization. **Creating new users is a capability, not a default right of every User** — see §3.3/§3.5: only Org Admin has it by default, and Admin can grant it to another role if a deployment needs delegated account creation.
- **Dreamline User** — an external/vendor role with read/write access. **Renamed from an earlier `ad_agency` draft** — same role, same scope, just the name the stakeholder actually uses. **For v1, Dreamline User has write access to every module within its organization (same breadth as `user`)** — module-level restriction to just PR/Mainline-Fan Page Media/Social Media is deferred to a later phase, not built into v1 (see §9 #1).
- **Other module-scoped roles** — Admin can define further roles (e.g. "PR Manager," "Ground Report Coordinator," "Voter List Manager"), each granted access to a specific subset of modules. Org Admin then assigns any of these existing roles to the users they create — Org Admin picks from the catalog but does not define new roles themselves (see §3.3/§9 #9–10).

## 3. Core Architecture: Multi-Tenancy + Hierarchical RBAC

This is the central design requirement and should be treated as a cross-cutting concern, not a per-feature one. There are two nested scoping layers: **organization** (which politician's data is this?) and **hierarchy subtree** (which branch of that politician's cadre created/owns this record?).

### 3.0 Admin is a separate account type, not a `User`
- `admins` table — a small, standalone table (expect a handful of rows: your own team, plus any scoped ops/dev staff) with its own Devise scope (`devise_for :admins, path: 'console'`), its own login route, and no `organization_id`, `parent_id`, or `role_id` at all. There's nothing to scope: every row in this table already has full platform authority by definition, so it doesn't participate in the `roles`/`role_permissions` system described in §3.3 — that system exists for the `User` side only. An `Admin` row also has a `tier` (`full` or `ops`) — see below.
- This is a deliberate split from `User` (where an earlier draft of this document modeled this platform-operator account as a `User` row with `organization_id: nil`). Keeping it a genuinely separate table means an org-scoped query against `users` can never accidentally include a platform-operator row — it's not a "nil organization_id, exempt from this check" special case to get right every time, it's architecturally impossible, which matters given how sensitive a cross-tenant leak would be here (§8a).
- **Naming note:** this model was called `SuperAdmin` in an earlier draft, to avoid colliding with the org-level role also called "Admin." That collision is resolved the other way instead: the org-level role (the Politician's full-access role within their own organization) is renamed **`org_admin`** (§3.3), which frees up the plain name **`Admin`** for this platform-operator account type. Unqualified "Admin" from here on means this platform account type (§3.0); "Org Admin" always means the org-level role (§3.3).
- Admin authenticates through its own route (`/console/sign_in`), not linked anywhere in the organization-facing UI, and lands in a separate Platform Console (§5a) rather than any organization's dashboard.
- **`tier` (`full` / `ops`):** most `Admin` rows are `full` tier (the core team — unrestricted, platform-wide). An `ops` tier exists for developer/support staff who should only operate within specific organizations rather than the whole platform, scoped via an `admin_organizations` join table (`admin_id`, `organization_id` — many-to-many, so one `ops`-tier Admin can be assigned to several organizations). The Platform Console filters everything (organizations list, data views, exports) down to just the assigned organizations for an `ops`-tier Admin. **Still open:** whether `ops` tier gets full admin-equivalent access (including delete) within its assigned organizations, or something more limited such as read-only — see §9 #20.
- **2FA (`devise-two-factor`) is deferred, not required for v1,** on this scope — revisit making it mandatory here once real voter data is live (§2).
- Wherever the rest of this document says "Admin does X" at the platform level (creates organizations, defines roles, views cross-org data), read that as "an authenticated `Admin`" (§3.0) — and wherever it says "Org Admin," that's the org-level `org_admin` role within `User` (§3.3).

### 3.1 Organizations (tenant isolation)
- `organizations` table — one row per Politician/campaign, with an `active` boolean (default `true`), a `current_party_id` (nullable — see §3.1b), and a `constituency_id`/`constituency_type` polymorphic pair (nullable — see §3.1c) tying the org to the Loksabha or Assembly seat it's actually contesting. Every `User` and every domain record belongs to exactly one `Organization` via `organization_id` — there's no "Admin" exception to carve out here, since the platform-level `Admin` isn't a `User` at all (§3.0).
- **Org Admin** is the root of a given organization's user hierarchy — typically the Politician and/or their chief of staff. **An organization can have multiple Org Admins from day one** — there is no cap of one; any of them has full org-wide RWU + delete.
- Every domain table (`Ticket`, `CadreActivity`, `GroundReport`, etc.) should carry `organization_id` directly (denormalized from the owning user) as a belt-and-suspenders guard against cross-tenant data leaks, in addition to the hierarchy scoping below — don't rely on hierarchy scoping alone to enforce tenant isolation.

### 3.1a Deactivation cascade
- Deactivating an organization (e.g. the Politician's account/campaign has ended) is a single toggle: `organization.active = false`. The moment that happens, **every user under that organization — at every level of the hierarchy — is immediately unable to log in or view any data**, with no need to touch each user row individually.
- Enforce this at two points: (1) Devise's `active_for_authentication?` on `User` should also check `organization.active?` (this check doesn't apply to `Admin` at all, since that model has no `organization_id` to check — §3.0), and (2) every Pundit scope's base query should be scoped to `organization.active == true` as a defense-in-depth check, in case a session is already live when deactivation happens.
- The same mechanism can be reused to deactivate a single branch of the tree (e.g. just one District Head and their descendants) later if needed, without being a v1 requirement.

### 3.1b Political Party tracking
- SAC-PAD targets individual Politicians, not parties — the same platform can (and will) host Politicians from different, even rival, parties as separate organizations, and a given Politician can change party affiliation over time without losing history.
- `parties` table — global reference data (`name`, `abbreviation`, `color`, `logo` via Active Storage `has_one_attached`), managed only by `Admin` (§3.0), shared across every organization the same way geography reference data is (§8).
- `party_memberships` table — history-preserving record of an organization's party affiliation over time: `organization_id`, `party_id`, `started_at`, `ended_at` (nullable — `nil` means currently active). Changing a Politician's party never overwrites or deletes the prior membership row; it closes the old row (`ended_at = now`) and opens a new one.
- `Organization.current_party_id` — a denormalized pointer to the currently-active party (kept in sync whenever `party_memberships` changes), so the common case ("what party is this Politician in right now?") doesn't require a join. `nil` means Independent (no party). The full affiliation history is always available via `party_memberships` even though `current_party_id` makes the common case fast.

### 3.1c Organization ↔ constituency (Loksabha/Assembly) link
- SAC-PAD only targets two election levels — Loksabha (parliamentary) and Assembly (state) — and a given organization's Politician contests exactly one of the two at a time, set once by `Admin` at onboarding. This determines which villages/assemblies that organization's own modules (Ground Reports' village picker, bulk-messaging's geography filter, RAG Mapping's rollup — §8) show by default.
- `Organization` gets a polymorphic `belongs_to :constituency` — two columns, `constituency_id`/`constituency_type` (`'Loksabha'` or `'Assembly'`) — rather than two separate nullable FK columns (`loksabha_id` + `assembly_id`) plus a redundant `office_level` enum. `constituency_type` alone already says which level applies, so there's nothing to keep in sync. Same technique already used for `Attachment` (§7), so it's a consistent pattern, not a new one — the one tradeoff is that a polymorphic reference can't be a real DB foreign-key constraint (Postgres can't enforce "exists in one of two tables"), so referential integrity rests on model validation rather than the database, same as `Attachment` already accepts.
- **Fixed for the organization's lifetime, not history-preserving.** Unlike `party_memberships` (§3.1b), there's no join table tracking a change in constituency over time — if a Politician's seat genuinely changes later (redistricting, moving from MLA to MP), `Admin` edits these two columns directly. Revisit with a history table only if that turns out to matter in practice.
- **Deriving villages/assemblies from the link** — not a plain `has_many`, since which one applies depends on `constituency_type`:
  ```ruby
  # on Organization
  def assemblies
    case constituency_type
    when 'Assembly' then Assembly.where(id: constituency_id)
    when 'Loksabha' then Assembly.where(loksabha_id: constituency_id)
    end
  end

  def villages
    Village.where(assembly_id: assemblies.select(:id))
  end
  ```
  An Assembly-level org sees just that one assembly and its villages; a Loksabha-level org sees every assembly under that Loksabha, and every village under all of them. Every module that needs "which villages/assemblies does this org operate in" calls `organization.villages`/`organization.assemblies` rather than re-deriving this branch logic itself.
- Multiple organizations (rival candidates) can share the same `constituency_id`/`constituency_type` — there's no exclusivity lock on a geography row, and there shouldn't be: two rival Politicians contesting the same seat each just reference the same shared `Assembly`/`Loksabha` row (§8), while their own content about any village in it stays separated by `organization_id` as usual (§3.4/§8a).

### 3.2 User hierarchy (within an organization)
- `users` table is self-referential: `parent_id` (nullable — `nil` for an organization's Org Admin, the root of that organization's tree). The platform-level `Admin` isn't in this table at all (§3.0), so there's no corresponding "nil for Admin" case here.
- Use a tree gem to get efficient `subtree_ids` / `descendant_ids` queries without recursive SQL in application code — **`closure_tree` is preferred over `ancestry` given the 10,000-concurrent-user target (§8b)**: it maintains an actual closure table with indexed ancestor/descendant pairs, which holds up better under concurrent subtree lookups than `ancestry`'s materialized-path string matching.
- Because nearly every authorized request runs a subtree lookup (§3.4), **cache each user's `subtree_ids` list** (Solid Cache or Redis) instead of recomputing it on every request, and invalidate that cache only when the hierarchy actually changes (a user is created, moved, or deactivated under them) — this is the single highest-leverage optimization in the whole RBAC design at this scale.
- **Confirmed: unlimited depth** — no cap on how many levels the tree can have (Org Admin → State → District → Taluka → Karyakarta → …).
- Whoever creates a `User` becomes its `parent`; see §3.3/§3.5 for who is actually allowed to create users (by default, Org Admin only — not every `User`).

### 3.3 Roles & permissions
Model roles as data (not a hardcoded enum) so new module-scoped roles can be added without a deploy — but **role definition itself is an Admin-only (developer) action for v1**, not a self-service feature for organizations:
- `roles` table: `id`, `name`, `slug`, `is_system` (boolean), `can_create_users` (boolean — see below). *(An `organization_id` column can exist for future per-org custom roles, but for v1 every role is global/shared across all organizations — only `Admin` creates rows here, so it is effectively always `nil`.)*
- `role_permissions` table: `role_id`, `module` (enum: `kitchen_cabinet`, `cadre_program`, `ground_reports`, `pr`, `mainline_fan_page_media`, `social_media`, `voter_lists`, `rag_mapping`), `access_level` (`none` / `read` / `write`).
- `User` has a `role_id` (instead of a hardcoded role column). This `roles` table is **only for the `User` side** — the platform-level `Admin` doesn't have or need a row here (§3.0).
- **Who creates roles:** only an authenticated `Admin` defines a role's name and its module/access-level grants (including whether it can create users) — this is effectively "the developer adds a role and its scope" (confirmed, §9 #10), done from the Platform Console (§5a). No Org-Admin-facing "create custom role" UI is in scope for v1.
- **Who assigns roles:** whoever creates a `User` picks which existing role to assign them, from the catalog `Admin` has defined. By default only Org Admin can create users (see `can_create_users` below), so in practice Org Admin is also the one assigning roles today.
- **`can_create_users` capability:** a boolean on `Role`, separate from module permissions, controlling whether that role may create new `User` records (and, in doing so, assign one of the existing roles to them). **Confirmed: not every role can create users — only `org_admin` has this by default.** If a deployment later needs a mid-tier role (e.g. a "Regional Coordinator") to create sub-users, `Admin` flips `can_create_users: true` on that role; no other code change is needed.
- **System roles**, seeded once and shared by every organization (note there is no platform-level `admin` row here — that's the separate `Admin` account type, §3.0):
  - `org_admin` — `write` on every module, within their own organization only, `can_create_users: true`, plus delete rights (soft delete only — see §3.4a).
  - `user` — `write` on every module, within their own subtree, `can_create_users: false`.
  - `dreamline_user` — **v1: `write` on every module**, within their own subtree (same as `user`), `can_create_users: false`. Renamed from `ad_agency` (§9). Narrowing this to PR / Mainline-Fan Page Media / Social Media only is a planned follow-up (§9 #1) — a `role_permissions` data change, not new code.
- Role is distinct from hierarchy position — the hierarchy determines *whose* data a user sees; the role's permissions determine *which modules* they can see at all, *what* they can do there (read vs. write), and whether they can create more users.

### 3.4 Data ownership & visibility rule
This rule governs `User` access only — `Admin`'s Platform Console is a separate set of controllers operating on `Organization` rows directly (with its own logged cross-org audit trail, §8a), not Pundit policies mixed into the same classes as organization data. That separation is part of the point of §3.0: there's no platform-level `admin?` branch mixed into `User` policies to remember.

- Every domain record (ticket, program, report, media item, etc.) belongs to the `User` who created it, via an `owner_id` (or `created_by_id`) foreign key, plus the denormalized `organization_id` from §3.1.
- **Visibility rule**, checked in this order, for any `User`:
  1. **Organization match** — a user never sees a record outside their own `organization_id`.
  2. **Module permission** — the user's role must have `read` (to view) or `write` (to edit) on that record's module; otherwise the module is invisible to them entirely.
  3. **Hierarchy subtree** — within an organization and a permitted module:
     - `org_admin` → sees every record in the whole organization.
     - `user` / any other non-`org_admin` role → sees records owned by themselves **and every descendant in their subtree** (recursive roll-up). This is the "create user under them, see only data related to them" requirement.
     - `dreamline_user` → same subtree rule as `user`, but only within the modules its role permits.
- Implementation sketch (Pundit policy scope, for `User` requests only):
  ```ruby
  class TicketPolicy < ApplicationPolicy
    class Scope < Scope
      def resolve
        return scope.none unless user.role.can?(:ticket, :read) # module permission check
        base = scope.where(organization_id: user.organization_id)
        user.org_admin? ? base : base.where(owner_id: user.subtree_ids) # subtree_ids includes self
      end
    end
  end
  ```
  An `Admin`-authenticated request never runs through `TicketPolicy` at all — Platform Console controllers query `Organization`/`Role`/cross-org reporting data directly, under their own (much simpler) authorization check: "is there an authenticated `Admin`."
- Every controller index/show action should go through a Pundit scope — there should be no module where a non-`org_admin` can query unscoped data (this includes the "Get All Details" and Excel export actions, which must honor the same scope, not bypass it).

### 3.4a Deletion is soft-delete only
- "RWU" is confirmed as Read/Write/Update. **Org Admin also has delete rights, but every delete is a soft delete** — no domain record (Ticket, CadreActivity, GroundReport, Voter, etc.) is ever hard-deleted from the database.
- Implementation: add a `deleted_at` (or `discarded_at`) timestamp column to every domain table, via the `discard` gem (preferred for Rails 8) or `paranoia`. All default scopes exclude soft-deleted records; Org Admin gets a separate "Trash"/"Archived" view per module to see and optionally restore them.
- Only Org Admin can soft-delete within the `User` side of the system; `user`/`dreamline_user`/custom roles get `write` (create/update) but not delete, unless a role is explicitly granted a `delete` capability later. `Admin`, from the Platform Console, has the separate ability to deactivate a whole organization (§3.1a), but doesn't normally do record-level CRUD on campaign data.
- Soft-deleted records should still be excluded from counts/charts/exports by default, and the deletion itself should be captured in the audit log (§8) — who deleted what, and when.

### 3.5 User management
- `Admin` (from the Platform Console, §5a) creates organizations, their initial Org Admin account(s), and every `Role` + its permissions (including `can_create_users`).
- Org Admin can create/edit/deactivate any user within their own organization, place them anywhere in the hierarchy (choose `parent_id`), and assign them any existing role from the catalog `Admin` defined.
- **By default, only Org Admin can create users.** A `user`-role (or other non-`org_admin` role) person cannot create sub-users unless `Admin` has explicitly granted that specific role `can_create_users: true` — this was a deliberate change from "every user can create sub-users": account creation is a capability gated by role, not an automatic right of being in the hierarchy. Because Org Admin can place a new user anywhere in the tree (not just directly under themselves), the hierarchy can still be arbitrarily deep even though Org Admin is doing all the creating.
- A non-`org_admin` (and any role without `can_create_users`) cannot create users, change their own role, re-parent themselves elsewhere in the tree, or move to another organization.
- Deactivating a user deactivates everything below them in the tree too — see §3.1a, which also covers the common case of deactivating the whole organization when a Politician's engagement ends.

## 5. Common UI/Functional Patterns

These appear on nearly every module screen in the wireframe and should be built as shared, reusable components rather than per-module one-offs:

- **Top bar:** app name/subtitle, logged-in user's photo, name, session timestamp, login count, settings menu.
- **Module toolbar:** `Export Excel` · `Prepare Chart` · chart-type toggle (`Bar` / `Pie` / `Line`) · `Export Chart` · `Get All Details`.
- **Left sidebar:** module-specific category/entity list (acts as in-module navigation/filter).
- **Center panel:** filterable data table with per-column filter icons, or a large text/attachment entry panel for report-style modules.
- **Attachments:** images, videos, photos attachable to records (Active Storage, polymorphic `has_many_attached`).
- All of the above must respect the hierarchy/role visibility rule from §3 — "Get All Details" means "all details I'm allowed to see," not literally all records in the table.

## 5a. Dashboards

Not a separate dashboard per role, except for one deliberate split at the top:

- **Organization Dashboard** — one shared dashboard, used by Org Admin, User, Dreamline User, and any other `User`-side role. Built as a set of independent widgets (open tickets by status, RAG summary, recent ground reports, cadre activity feed, reach trend, etc.), where each widget's query runs through the exact same Pundit scoping (§3.4) as every other screen, and whether a widget renders *at all* reuses the existing module `role_permissions` check (§3.3) — a role with no access to Voter Lists simply doesn't get that widget. This means Org Admin (full module access, whole org) and Dreamline User (v1: full module access, own subtree) see the same dashboard framework with naturally different content, without any role-specific dashboard code. Org Admin additionally gets a small number of org-admin-only widgets not tied to a module — pending items needing attention, a hierarchy/user-count summary, a recent-deletions feed (tying into §7a's audit trail) — gated by the `can_create_users`/`org_admin` capability rather than a module permission, but still on the same dashboard.
- **Platform Console** — a genuinely separate section of the app, for `Admin` only (§3.0). `Admin`'s job (operating the platform across every organization, or — for `ops` tier — a scoped subset of it) is categorically different from running one campaign, so this isn't "the Organization Dashboard with more data" — it's its own set of screens: organizations list/health (active/inactive, user counts, last activity), create organization + initial Org Admin, the Role/permission catalog editor (§3.3), the Party catalog editor (§3.1b), the Kitchen Cabinet ticket-category catalog editor (§6.1), the cross-org audit log (§8a), and platform operational health (daily sync job success rate, queue depth, API rate-limit headroom with Meta/WhatsApp). Reached only through the separate Admin login (§3.0), never linked from the Organization Dashboard.

## 6. Modules (Feature Areas)

### 6.1 Kitchen Cabinet
Tracks local civic issues/grievances raised by constituents. The flow: a person comes to meet the Politician (or a cadre member) with an issue, a `User` logs it as a `Ticket`, the org works the issue, and once it's actually resolved, the record becomes a permanent, attributable proof of help delivered to that person.

**Categories (`TicketCategory`) — global, Admin-managed, extensible.** All of the following render as sidebar submenu items under Kitchen Cabinet, not a hardcoded enum: Health, Road & Transport, Water, MSEB/Electricity (power), Student, Police Station, Farmers, Events & Camps, Personal Help, Personal Connect, Functions – Weddings/Birthdays, and **Other** as a catch-all — 12 seeded categories. `TicketCategory` is a shared/global reference table (`id`, `name`, `slug`, `active`, `display_order`), managed only by `Admin` (§3.0) — the same pattern as `Role` (§3.3) and `Party` (§3.1b): one shared catalog across every organization, even though the `Ticket` records filed under each category remain fully org-scoped (§3.4). `Admin` can add further categories later without a deploy or code change.

**Navigation:** clicking a category in the sidebar filters the center table to that category's tickets (still scoped to the viewer's org/subtree, same as every other module per §3.4), with the standard module toolbar (§5) — Export Excel, Prepare/Export Chart — plus "create new ticket," pre-filled to that category.

**Record fields (`Ticket`):** `ticket_number`, `ticket_category_id`, Person/Represents (name + village), Mobile Number, `description` (free-text writeup of the issue, distinct from attachments), Attachment(s), `voter_id` (gated — see below), Reported Date, Closure Date, Village/Ward, Nature of Issue, Reported Value, `status`.

**Status enum:** `open` / `in_progress` / `closed` / `blocked`.

**Voter ID capture is gated on resolution — the key business rule for this module.** A `voter_id` can only be set or updated once a ticket's `status` is `closed` — enforced as a model-level validation, not just a UI hint, so it's not possible to persist a `voter_id` on a still-open, in-progress, or blocked ticket. This is deliberate: a `voter_id` on file is proof the org actually delivered help to that person, not just that help was requested. Practically, it also builds the list of "who we've helped in this village" for the Politician to reference on a future visit, and the `voter_id` is the join key that later links a resolved `Ticket` to the Voter Lists module (§6.7) — a planned loose lookup (`Ticket.voter_id` ↔ `Voter.voter_id`), not an enforced FK, since Voter data is bulk-imported and may not always have a matching row.

**Follow-up / action report (`TicketFollowUp`):** a running, timestamped log of what's actually been done on a ticket — `ticket_id`, `note` (free text describing the action taken), `created_by_id`, `created_at`, optional attachment. Multiple entries accumulate over a ticket's life, forming the per-ticket "what did we do about this" report — distinct from §7a's `TicketStatusChange`, which only logs bare status transitions, not substance. Any role with `write` on the Kitchen Cabinet module can add a follow-up entry; no new capability needed.

- Each ticket is owned by the user who logged it; closure date tracks resolution.

### 6.2 Cadre Program
Tracks party-organizing activity for the person/cadre using the account, across six categories whose columns genuinely differ from each other — not just minor variations — so the schema is a **shared base table + per-category detail tables**, the same pattern used for Kitchen Cabinet's category/ticket split (§6.1), rather than either one giant table or six fully independent ones. Six independent tables would mean duplicating Pundit scoping, soft-delete, audit history, and the dashboard activity feed six times over, and "show recent cadre activity" would become a six-way UNION instead of one query; one single wide table would mean dozens of columns sitting null for 5 of 6 rows, since the categories' fields are genuinely different, not just cosmetically.

**Categories (fixed, not Admin-extensible — unlike Kitchen Cabinet):** Program By Party, Leadership Meets, Party Programs Hosted, Personal Program, Personal Activities, One To One. Unlike `TicketCategory`, there's no benefit to making this list dynamically addable: each category already needs its own bespoke columns, so a 7th category would always need a new detail table and code regardless of whether the category name itself lives in a database row or a hardcoded enum.

**`CadreActivity` (base table)** — holds what's common to all six categories: `owner_id`, `organization_id`, `category`, `impact_notes` (rich text — the real-world political impact/outcome of the activity: sentiment, local reaction, whether it's likely to move votes; this is the field labeled "Media Value" in the wireframe, kept distinct from each detail table's own operational `notes`), Photos (`has_many_attached`, Active Storage), plus the standard soft-delete/audit columns (§3.4a/§7a). This is what Pundit scoping, the dashboard's cadre activity feed (§5a), and Excel export all key off of.

**Detail tables** (`belongs_to :cadre_activity`, one `has_one` per category — two categories share an identical shape, so five tables cover six categories):
- `CadreActivityProgram` (shared by **Program By Party** and **Personal Program**) — `program_name`, `occasion`, `location`, `occurred_on`, `host`, `notes`.
- `CadreActivityLeadershipMeet` — `whom_to_meet`, `point_of_discussion`, `work_submitted`, `submitted_on`, `followup_on`, `resolution_notes`.
- `CadreActivityPartyProgramHosted` — `program_name` (Andolan), `hosted_on`, `location`, `total_attendees`, `print_media`, `electronic_media`.
- `CadreActivityPersonalActivity` — `activity_name`, `occasion`, `total_submission`, `from_date`, `to_date`, `notes`.
- `CadreActivityOneToOne` — `karyakarta_user_id` (FK to `User`, indexed — a real reference, not free text, so per-karyakarta rollups like "how many one-to-ones has this person logged" stay reliable even at millions of rows), `karyakarta_name_text` (nullable fallback for a person not yet entered as a `User`), `assignment`, `resolved` (boolean), `from_date`, `to_date`, `notes`.

The `CadreActivity` ↔ detail-table join is a cheap indexed primary-key/foreign-key lookup regardless of row count — this holds up fine at millions of rows per §8b's existing indexing/pagination/read-replica guidance, with no partitioning or denormalization needed unless a table grows well past tens of millions of rows.

### 6.3 Ground Reports
Village-centric, not record-centric: a `User` lands on this module by selecting a **Village** first (the shared geography reference entity, §8), and the page is organized into sub-sections about that village — Report, Mock Poll, Worship Places, Yatra, Political Position, and Local Contacts. The village itself is shared reference data, but every piece of content *about* it below is fully org-scoped (`organization_id` on every table) — the same split as Kitchen Cabinet categories vs. tickets: two rival politicians tracking the same real village each get their own completely separate rows, never shared.

- **Report** — reuses the existing `GroundReport` entity (`village_id`, `organization_id`, `owner_id`, `issue_text`, `resolution_text`, `reported_at`) for issues the team finds in that village and their resolutions, plus a new child entity `GroundReportTestimonial` (`ground_report_id`, `person_name`, `content_type`[`text`/`audio`/`video`], `text_content`[nullable], media attachment[Active Storage, nullable — handles the audio/video file directly], `created_by_id`, `created_at`) — feedback from villagers, one `GroundReport` can have many.
- **Worship Places** — `WorshipPlace` (`village_id`, `organization_id`, `name`, `type`[temple/mosque/church/etc. — not limited to temples], `notes`).
- **Yatra** — `VillageYatra` (`village_id`, `organization_id`, `notes`[rich text/text area], `updated_by_id`, `updated_at`). Deliberately **not** a dated event log — yatras don't recur on a fixed date, and the team doesn't want to track individual occurrences, just maintain one general, editable note per village (e.g. "generally happens in March") — one row per village per organization, edited in place over time.
- **Political Position** — `VillagePoliticalPosition` (`village_id`, `organization_id`, `party_id`[FK to `Party`, §3.1b — reuses the existing Party catalog rather than free text], `representative_name`, `position_title`[e.g. "Sarpanch"], `started_at`, `ended_at`[nullable = current]) — history-preserving, the same shape as `PartyMembership`, since the locally-ruling party changes after panchayat elections and the history matters, not just the current state.
- **Local Contacts** — two genuinely different kinds of people, corrected from an earlier draft that conflated them: **local karyakartas are not system `User` records** (a karyakarta living in a village isn't necessarily anyone with a login), so this is two standalone contact tables, not a `village_id` column on `User`:
  - `VillageLocalKaryakarta` (`village_id`, `organization_id`, `name`, `phone`, `notes`) — karyakartas who live in that village, logged purely as contact info.
  - `VillageLocalAdminContact` (`village_id`, `organization_id`, `name`, `role_title`[free text: Sarpanch, Gram Sevak, Police, CO, etc.], `phone`, `notes`) — non-system administrative contacts (renamed from an earlier `VillageLocalContact` draft, to read as the sibling of `VillageLocalKaryakarta` above rather than a generic catch-all).
- **Mock Poll — resolved.** The team uploads an Excel of raw village-level survey data; each respondent row becomes a `MockPollResponse` (`village_id`, `organization_id`, `politician_id`[FK to `Politician` — §6.3a], `respondent_name`, `respondent_mobile`[optional], `preference_basis`[enum: `individual`/`party` — why the respondent is leaning that way, since many people vote for the party without knowing the candidate], `vote_intent`[boolean, nullable — `true`=yes, `false`=no, `nil`=undecided/unknown], `note`, `created_by_id`, `created_at`). One respondent can have multiple rows — one per `politician_id` they were asked about — rather than one wide row per respondent, so a single Excel import naturally produces several `MockPollResponse` rows per person surveyed. "Who's likely to win" is computed on read by grouping `MockPollResponse` by `village_id` + `politician_id` + `vote_intent` — no separate tally table needed at this stage; revisit with a precomputed rollup (like `RagEntry`, §7) only if per-village volumes get large enough that computing it live becomes slow.
- Notable: this module explicitly supports an external **Reporting Agency** importing survey data for the Report sub-section (and now Mock Poll too) — needs its own scoped import permission.

### 6.3a Politician (opponent tracking)
- A small, org-scoped catalog of the Politicians relevant to that organization's campaign — its own candidate plus any opponents — used first by Mock Poll (§6.3) and by Opposition Pages comparisons (§6.5), and expected to be referenced from further places as the opponent-tracking need shows up elsewhere (still open — see §9).
- `Politician` (`id`, `organization_id`, `name`, `party_id`[nullable FK to `Party`, §3.1b — a plain snapshot field for categorization, not history-preserving like `party_memberships`], `is_own_politician`[boolean, default `false`], `photo`[optional, Active Storage], `discarded_at`, `discarded_by_id`). **Org-scoped, not global** — unlike `TicketCategory`/`Party`/`PrCategory`, each organization manages its own roster, since "who are Org A's opponents" has no meaning shared across organizations.
- **Managed by `Admin`, both at onboarding and ongoing** — `Admin` adds the organization's own Politician plus any known opponents when the organization is created, and can add/edit/retire (soft-delete) entries later as the field changes, from the Platform Console (§5a). Not an Org-Admin-facing feature for v1.
- **Exactly one `Politician` per organization has `is_own_politician: true`**, enforced via a partial unique index (`WHERE is_own_politician = true`), and that row's `name` is kept in sync with `Organization.name` by a model callback, so the two can't silently drift apart from being edited in two different places.

### 6.3b Geography reference data
Four global, Admin-managed reference tables, seeded once and shared across every organization — the same pattern as `Role`/`Party`/`TicketCategory` — forming the hierarchy already used by Voter Lists' filters (§6.7) and now by Ground Reports and the `Organization` constituency link (§3.1c):
- `State` (`id`, `name`)
- `Loksabha` (`id`, `state_id`[FK], `name`) — parliamentary constituency
- `Assembly` (`id`, `loksabha_id`[FK], `name`) — state constituency
- `Village` (`id`, `assembly_id`[FK], `name`)

These are reference-data-only — nobody writes "business data" onto a `Village`/`Assembly`/`Loksabha` row itself; every piece of org-specific content about one of them (`GroundReport`, `VillageYatra`, `VillagePoliticalPosition`, `WorshipPlace`, `VillageLocalKaryakarta`, `VillageLocalAdminContact`, `MockPollResponse`) lives in its own org-scoped table, keyed by both the geography FK and `organization_id` (§3.4/§8a) — so two rival organizations referencing the exact same `Village` row never share or see each other's content about it.
- **Still open:** whether `Voter` (§6.7/§7), which currently stores `state`/`loksabha`/`assembly`/`village` as flat text since it's bulk-imported from election rolls, should be migrated to FK into this hierarchy too, or stay flat text because matching bulk-imported names against the new tables reliably is its own project — see §9.
- **Uniqueness note for the org-scoped village tables above:** any DB-level uniqueness constraint on these must be composite — `(village_id, organization_id)`, never `village_id` alone — so that one organization covering a village never blocks another organization from having their own row for that same village. Concretely: `VillageYatra` needs a unique index on `(village_id, organization_id)` (one note per village *per org*), and `VillagePoliticalPosition`'s "only one currently-active row" rule must be scoped to `(village_id, organization_id)` where `ended_at IS NULL`, not to `village_id` globally.

### 6.4 PR
Traditional media monitoring across six categories — **Electronic Media (Main Line), Print Media, Local Print, Local Electronic, Outdoor Media, Podcasts/Interviews.** Unlike Cadre Program (§6.2), where every category genuinely needed its own bespoke columns, comparing these six side by side shows most of them share an *identical* shape — so this ends up as one base table plus just **two** thin detail tables, not six.

**Categories (`PrCategory`) — global, Admin-managed, extensible,** same pattern as `TicketCategory` (§6.1): shared catalog across every organization, 6 seeded categories, sidebar navigation filters the center table to that category same as Kitchen Cabinet.

**`PrRecord` (base table)** — holds every field common across categories: `owner_id`, `organization_id`, `pr_category_id`, `title`, `description`, `media_platform_id`[nullable FK to `MediaPlatform`], `media_platform_name_text`[nullable free-text fallback], `url`[nullable — link to the news article/video/YouTube/podcast], `sentiment`[enum: `positive`/`negative` — the column the wireframe called "news_type"; renamed to be unambiguous about what it actually records], `published_on`[date — every category needs a date, so this is the one shared field for it], `thumbnail_url`[nullable — see open item below], Attachments (`has_many_attached`, Active Storage — audio/video/photos), plus the standard soft-delete/audit columns (§3.4a/§7a).

**`MediaPlatform`** — global, Admin-managed catalog (name/slug/active), the same FK-with-free-text-fallback pattern already used for `CadreActivityOneToOne.karyakarta_user_id` (§6.2): Electronic Media and Print Media use `media_platform_id` since those outlets are known and controllable; Local Print and Local Electronic use `media_platform_name_text` only, since the team can't enumerate every hyperlocal paper/channel up front; Podcasts/Interviews also uses the free-text column for the podcast's channel name.

**Detail tables — only two of the six categories need one:**
- **Electronic Media, Print Media, Local Print, and Local Electronic have no detail table at all.** Every field the wireframe described for these four (title, description, platform, link, attachments, sentiment) is already on the `PrRecord` base — they're distinguished purely by `pr_category_id`.
- `PrRecordOutdoorAdCount` (`pr_record_id`, `outdoor_ad_type_id`[FK to `OutdoorAdType`], `count`) — Outdoor Media needs structured counts per physical ad type (flex, board, pole kiosk, …), and one `PrRecord` can have several (e.g. both flex banners and boards), so this is a `has_many` child table rather than extra base columns. `OutdoorAdType` (`id`, `name`, `slug`, `active`) is the one genuinely free-to-extend catalog here — Admin adds a new ad type with just a name, no schema change.
- `PrRecordPodcast` (`pr_record_id`, `recorded_on`) — Podcasts/Interviews is the one category needing a *second* date (`published_on` on the base covers the publish date; this adds the recording date). Channel name and link reuse the base's `media_platform_name_text`/`url`.

**Thumbnail fetching** (showing a thumbnail of the news/video when an Electronic Media record is created) is flagged as an **open engineering spike, not a schema blocker** — `thumbnail_url` already exists on the base to hold the result once a fetching approach (oEmbed, link-preview service, or a per-platform scraper) is chosen; see §9.

**Export:** reuses the existing per-category Excel export already built for every other module's sidebar-category pattern (§5) — "export all PR data for this category" needs no new mechanism.

### 6.5 Mainline/Fan Page Media — deferred to v2
**Confirmed: this entire module moves to v2, same treatment as Targets (§6.9).** Facebook & Instagram page tracking for Official Pages, Fan Pages, Opposition Pages, and Comparisons — with automated daily metric collection via the Meta Graph API and a Reach Dashboard — is not built for v1. The design below is preserved for when that phase is scoped; nothing here blocks v1 planning.

- **Sidebar categories:** Official Pages, Fan Pages, Paid Promotions, Reports, Opposition Pages, Comparisons.
- **Platforms tracked:** Facebook, Instagram, WhatsApp (WhatsApp has no public insights API — see note below).
- **Fields:** Testimonials with attachments; comparison view against Opposition Pages.
- `SocialPage.politician_id` (nullable FK to `Politician`, §6.3a) — links an Opposition Page to a tracked opponent, so the Comparisons view ties back to a named `Politician` row instead of an unlinked label. Nullable since it doesn't apply to Official/Fan/karyakarta pages. Ships with this module in v2.
- The `SocialPage`/`SocialPageMetricSnapshot`/`SocialPagePost` tables themselves are **not** deferred — they're built for v1 to serve Karyakarta Pages (§6.6), and this module simply reuses them for Official/Fan/Opposition pages once v2 comes around, with no schema change needed at that point.

**Design for v2, preserved as-is:**
- For every page/account registered under Official Pages (and any Fan Page the organization has been granted access to), connect via the **Meta Graph API** (Facebook Pages API + Instagram Graph API for linked Instagram Business/Creator accounts) and pull data **daily** via a scheduled job (Solid Queue recurring task).
- **Metrics to capture per page, per day:** follower/fan count, number of posts published that day, views/impressions, and reach split into **organic reach vs. paid reach**. Weekly/monthly/yearly figures are *rolled up from the daily snapshots* (sum/average over the period), not captured separately — store daily granularity once, aggregate on read.
- **Reach by category:** the wireframe asks to "check post reach based on category." Sliced via `SocialPagePost` (platform post ID, posted-at, post type/category, organic reach, paid reach, views, `likes_count`, `comments_count` — §6.6). **"Category" itself needs a definition pass** (post format like photo/video/reel, or a content topic tag the team assigns) — flag for confirmation before building.
- **Reach dashboard:** a dedicated trend dashboard (follower growth over time, organic vs. paid reach split, post-category breakdown, comparison across the organization's own pages) — likely its own sub-view within this module, following the same List/Chart/Dashboard pattern already used in RAG Mapping (§6.8).

**Important constraint to flag before building (confirm with stakeholder):** Meta's Graph API only exposes detailed Insights data (reach, impressions, organic-vs-paid breakdown, per-post metrics) for Pages and Instagram accounts the connecting app has been **granted admin/Insights access to** — i.e. the organization's own Official Pages, and any Fan Page willing to add the app as an admin. It does **not** expose that level of detail for pages the organization doesn't manage. This means:
- **Official Pages / cooperating Fan Pages** — full automated daily pull as described above is realistic.
- **Opposition Pages / Comparisons** — Meta does not provide competitor insights through the API. Only basic public data (e.g. public follower/fan count, if still exposed on that endpoint) can be pulled, if at all; organic-vs-paid reach and post-level detail for pages you don't manage are not obtainable this way. Scraping a competitor's page to get around this is against Meta's Terms of Service and is **not** something to build. The "Comparisons" feature will need a fallback (manual entry of whatever public numbers are visible, or dropping the organic/paid breakdown for those rows) — needs a decision before implementation.
- Also note: the app will need Meta App Review approval for the `read_insights` / `instagram_manage_insights` permissions before this works in production for any page beyond the developer's own test pages — this is a lead-time item, not just a coding task.
- **WhatsApp** has no comparable public insights API for page-style analytics; its presence in this module is likely limited to the Bulk WhatsApp/SMS messaging features covered under Social Media (§6.6), not automated metric pulls.

### 6.6 Social Media
Broader social operations and outreach tooling. **With Mainline/Fan Page Media deferred to v2 (§6.5), this module carries the large-scale, many-pages functionality for v1** — Karyakarta Pages is the registry of the potentially hundreds/thousands of individual Facebook/Instagram pages run by cadre members, and that's where bulk cross-posting lives.
- **Sidebar categories:** Karyakarta Pages, Influencers, Paid Promotions, Tag Accounts, Bulk WhatsApp/SMS, IVRS.

**Karyakarta Pages — registry + one-click bulk posting + per-post reporting:**
- Each karyakarta's Facebook/Instagram page is a `SocialPage` row (`page_type: "karyakarta"`), connected via the Meta Graph API flow — each page owner (or the Org Admin, on their behalf) must complete a Facebook "connect this Page" OAuth step so the app holds a valid, encrypted access token for it (see the open question on who does this at scale, §9 #13).
- **The karyakarta who owns the page isn't necessarily a system `User`** — same correction as Local Karyakartas (§6.3a). `SocialPage` gets the same FK-with-fallback pattern used for `CadreActivityOneToOne`/`VillageLocalKaryakarta`: `karyakarta_user_id` (nullable FK to `User`) + `karyakarta_name_text`/`karyakarta_mobile_text` (fallback). `owner_id` stays as "which of our team members manages this entry in our system" — a different person, potentially, than the karyakarta who actually owns the Facebook page.
- **Compose once, publish to many:** a `BulkPost` is authored once (text, image/video, optional link) and fanned out to a chosen set of target pages — all karyakarta pages, a filtered subset (e.g. one district's pages, via the hierarchy/geography already modeled), or an explicit multi-select.
- Each target page gets its own `BulkPostTarget` row (status: pending/success/failed, the resulting platform post ID once published, error message if it failed) so a partial failure (e.g. one karyakarta's token expired) doesn't block the other pages and can be retried individually.
- Fan-out is **asynchronous** (one background job per target page via Solid Queue), not a single synchronous loop — publishing to hundreds/thousands of pages takes real API calls and must respect Meta's rate limits (per-app and per-page), so "one click" means "one click to kick off a job that finishes publishing over the next several minutes," with a live status view (e.g. "142/150 published, 6 pending, 2 failed — retry").
- **Per-post reporting:** once published, each target's post is tracked via `SocialPagePost` (one row per page per post) — `organic_reach`, `paid_reach`, `views`, plus explicit `likes_count` and `comments_count` columns (replacing the earlier, vaguer `engagement` field) so reach, likes, and comments are each independently queryable per post, not folded into one number.
- This reuses the existing module-permission system (§3.3) rather than needing new role mechanics — whichever role has `write` on the Social Media module can trigger a bulk post; Dreamline User has it too under the current v1 decision (§9 #1) unless that's narrowed later.

**Influencers — outreach log, not an API integration:**
- Different enough from Karyakarta Pages that it needs its own entities rather than reusing `SocialPage` — an influencer's page isn't one the org has API/token access to, so there's no automated metric pull, only manually-entered "raw data" after asking them to publish.
- `Influencer` (`id`, `organization_id`, `name`, `mobile`, `platform`, `page_url`, `assembly_id`[nullable FK — which assembly they're relevant to; rolls up to Loksabha via `assembly.loksabha_id` for Loksabha-level organizations], `follower_count_estimate`, `notes`, soft-delete columns).
- `InfluencerPost` (`id`, `influencer_id`, `organization_id`, `requested_on`, `post_url`, `reach`, `likes_count`, `comments_count` — all manually entered, nullable, `screenshot`[Active Storage], `notes`, `created_by_id`, `created_at`).

**Paid Promotions, Tag Accounts** — Paid Promotions explicitly "add later," not detailed yet; Tag Accounts has no detail yet either — both left as the generic campaign/outreach log placeholder (channel, audience, date sent, response count) pending confirmation.

**Bulk WhatsApp/SMS — resolved design, both channels together:**
- Goal: send bulk/broadcast messages, in one click, to multiple named groups or individual people — targeted either by geography (village/assembly/loksabha, via `organization.villages`/`organization.assemblies`, §3.1c) or by an explicit, reusable contact list. WhatsApp and SMS are treated as two channels of the same feature rather than two separate ones.
- `BulkMessage` (`id`, `organization_id`, `channel`[`whatsapp`/`sms`], `template_id`/`body`, `target_type`[`geography`/`contact_group`/`explicit`], `target_ref`, `created_by_id`, `created_at`, `status`).
- `BulkMessageTarget` (`bulk_message_id`, `recipient_name`, `recipient_mobile`, `status`[`pending`/`sent`/`delivered`/`failed`/`invalid_number`], `sent_at`, `error_message`) — same per-recipient tracking shape as `BulkPostTarget`.
- `ContactGroup`/`ContactGroupMember` (`organization_id`, `name` / `contact_group_id`, `name`, `mobile`) — a named, reusable audience list (e.g. "Booth 12 Karyakartas," "District Volunteers") for the "multiple groups" case, separate from geography-filtered targeting; when the audience is geography-based, recipients are resolved from the `Voter` table (§6.7) by the selected village/assembly/loksabha.
- **Vendor note:** a paid WhatsApp Business service (a BSP like Gupshup/Twilio/Interakt, or Meta's own Cloud API directly) is planned — which one decides the integration work, not the schema. One real constraint either way: WhatsApp's Business API can message individual opted-in contacts but **cannot** post into an actual WhatsApp *Group* chat (that's a personal-account-only feature) — so "groups" here means named contact lists (`ContactGroup`), not literally posting into someone's WhatsApp Group. Template approval, tiered volume limits, and consent/opt-in for numbers sourced from `Voter` all still apply (§8a's legal/compliance note) and should be confirmed before this ships.

**IVRS — automated voice broadcast with response tracking:**
- Goal: record (or script, if using text-to-speech) a message, target it by village/assembly/loksabha (same §3.1c scoping as Bulk WhatsApp/SMS), and call every matching number, with the call outcome tracked per recipient.
- `IvrsCampaign` (`id`, `organization_id`, `name`, `recorded_message`[Active Storage audio, or a TTS script text field], `target_filter`[village/assembly/loksabha], `created_by_id`, `created_at`, `status`).
- `IvrsCallAttempt` (`ivrs_campaign_id`, `recipient_mobile`, `call_status`[`delivered`/`listened_fully`/`listened_partial`/`invalid_number`/`rejected`/`no_answer`/`busy`], `attempted_at`, `duration_seconds`).

### 6.7 Voter Lists
Electoral roll lookup, plus voter sentiment capture tied to Kitchen Cabinet resolution.
- **Filters:** Select State → Select Loksabha (parliamentary constituency) → Select Assembly (state constituency) → Select Village → Select Booth → `Open List`.
- **Output:** voter list appears in the center panel once filters are applied, paginated (`Pagy`, §8b) — can run into millions of rows for a full state.
- **`organization_id` correction:** `Voter` is org-scoped like every other domain table (§3.1), not shared reference data like `Village` — each organization bulk-imports and owns its own copy of the roll relevant to it. This matters now that sentiment (below) is tracked per voter: a rival politician in the same constituency would read the same real voter completely differently, so that can't live on a shared row.
- **`booth_id`, not a flat booth number** — booth numbers repeat across different assemblies/loksabhas, so `Voter.booth_id` is a real FK to `Booth` (§6.3b), not a plain integer. This means whatever does the bulk import has to resolve each row to the correct `Village` (and thus the correct `Booth`) to assign this field correctly — a real data-quality step for the importer, not just a UI filter concern, even though `Voter`'s other geography fields (`state`/`loksabha`/`assembly`/`village`) stay flat text for now (§9 #34).
- **Voter sentiment, captured at Kitchen Cabinet ticket resolution:** `Voter` gains `sentiment_status` (enum: `pleased`/`displeased`/`transit`, nullable, mutable — a voter can move between any of these later, e.g. Pleased → Displeased after a bad experience), `sentiment_updated_by_id`, `sentiment_updated_at`. When a `User` closes a `Ticket` and sets its `voter_id` (§6.1), the same step shows the matched voter(s) and asks the resolver to pick Pleased/Displeased/Transit, writing straight to that `Voter` row. Green/Amber/Red is a fixed presentation mapping off this enum (pleased→green, transit→amber, displeased→red), not a separately stored color field. Full history of how a voter's sentiment changed over time comes for free from the Tier 1 `VoterVersion` PaperTrail history already planned for `Voter` (§7a) — no separate status-log table needed.
- Contains sensitive PII (Voter ID, names, possibly mobile numbers) — see §8 security note.
- **Still open:** how `Voter` rows actually get into the system — presumably a bulk Excel/roll import (same `roo`/`creek` tooling already used for Ground Reports), done by `Admin` or a scoped import role, but whether this is a one-time onboarding seed, a periodic re-sync, or Org-Admin-triggered has never been specified.

### 6.8 RAG Mapping
Constituency-level risk/opportunity dashboard.
- **Views:** Mapped List, Chart, Dashboard.
- **Output:** list with Red/Amber/Green color coding, counts per category, and chart-based reporting — a rollup of Kitchen Cabinet + Ground Reports + Cadre Program activity per village/constituency, **plus a voter-sentiment rollup**: count of Pleased/Displeased/Transit voters (§6.7) per village/booth/assembly, feeding the same `RagEntry` shape (`color_status`, `count`, `computed_at`, §7) it already has. This is what turns "how many votes we got" into a straightforward count of Green (Pleased) voters at whatever geography level is being viewed.

## 7a. Audit History & Change Tracking

Two different tiers, not one blanket policy — matched to what's actually useful per table rather than diffing every field everywhere:

- **Tier 1 — full version history**, for records where the actual field-level history matters for accountability or compliance: `Voter` (PII edits), `User` and `RolePermission` (who changed someone's role or a permission grant), and candidates like `GroundReport` content edits. Implemented via `paper_trail`'s **custom version classes** — each tracked model gets its own dedicated table (`VoterVersion`, `UserVersion`, `RolePermissionVersion`, …) rather than one shared `versions` table every edit across the platform writes into. This spreads write/index load per table instead of concentrating it on one mega-table, and makes "show me this record's full history" a direct lookup on `item_id` rather than a polymorphic filter. PaperTrail sees a soft delete (`discard` setting `discarded_at`) as an ordinary tracked update, so the trail survives archiving rather than stopping at it.
- **Tier 2 — lightweight status-transition log**, for workflow-style tables where status is what matters, not every field edit: `Ticket` (confirmed) via `TicketStatusChange` (`ticket_id`, `from_status`, `to_status`, `changed_by_id`, `changed_at`). One row per status change, not per edit — cheap to store and query, and directly answers "how long did it take to move from Open to Resolved" by diffing consecutive `changed_at` timestamps, or total resolution time from `Ticket.reported_at` to the final transition. "Who created it" and "who soft-deleted it" don't need a version table at all for these — plain `owner_id`/`created_by_id` and the `discarded_by_id` column added alongside `discarded_at` (§3.4a) already answer that. **Still open:** whether `GroundReport`'s resolution workflow and `BulkPostTarget`'s pending/success/failed status should get the same lightweight treatment (§9 #16) — not yet decided table-by-table. Note `TicketFollowUp` (§6.1) is a different thing from `TicketStatusChange` — the former is a substantive, free-text action log ("what did we do about this issue"), the latter only timestamps bare status transitions; both exist for `Ticket` side by side.
- **Cross-table index — `ActivityLog`** (`actor_id`, `actor_type`[User/Admin], `action`, `record_type`, `record_id`, `organization_id`, `created_at`, no full diff): a small, append-only table populated alongside both tiers above, whose only job is answering "show me everything this person did, anywhere" without having to query N per-model version tables. This is also where `Admin`'s logged cross-org access (§8a) lives.

## 8. Non-Functional Requirements

- **Audit/activity trail:** every login records a timestamp and increments a login counter (shown in the top bar per the wireframe); every record create/update should be timestamped and attributable to a user. See §7a for the two-tier design (full version history vs. lightweight status-change log) and the cross-table `ActivityLog`.
- **Export:** every module supports exporting the currently filtered table to Excel, and exporting the generated chart (Bar/Pie/Line) as an image/PDF.
- **Import:** Ground Reports supports bulk Excel import, intended for use by an external reporting agency — this import path must still respect ownership/scoping (imported rows are owned by the importing user or their designated village/branch).
- **Geography reference data:** State → Loksabha (parliamentary constituency) → Assembly (state constituency) → Village (`State`/`Loksabha`/`Assembly`/`Village` tables, §6.3b) is used across Voter Lists, Ground Reports, the `Organization` constituency link (§3.1c), and RAG Mapping — modeled as shared, global, Admin-managed reference tables rather than duplicating free-text fields per module. `Voter` itself still stores this as flat text for now — see §9 #34.
- **Sensitive data handling:** Voter ID, mobile numbers, and personal details are PII. Access to the Voter Lists module and any export containing this data should be restricted and logged regardless of role (this is flagged for legal/compliance review, not just engineering).
- **Deactivation cascade:** deactivating an organization (a Politician's account) must immediately block login and data visibility for every user under it, at every level, without a separate step to deactivate each one (§3.1a).
- **Daily social-media sync job (§6.5):** a scheduled job pulls Facebook/Instagram metrics once per day for every page the organization has API access to; it must be idempotent (safe to re-run for the same day without duplicating snapshot rows), tolerate individual-page failures without aborting the whole batch, and log/alert when a page's access token has expired or been revoked (Meta tokens expire and need periodic refresh). Page access tokens are stored encrypted (§2) and are never exposed to non-Org-Admin roles.

## 8a. Security & Tenant Isolation (Critical)

This is political campaign data — grassroots issue reports, cadre activity, and voter PII — for what may be rival politicians from competing parties on the same platform (§3.1b). A cross-tenant leak (one Politician's Org Admin seeing another's data) isn't an ordinary bug here, it's the kind of failure that could end the product. No system can be honestly promised "100% leak-proof," but the goal is to make a leak require multiple independent things to fail at once, not just one missed `where(organization_id: ...)` clause in one controller. Concretely:

- **Defense in depth, not one layer.** §3.1/§3.4 already call for (a) a Pundit policy scope on every controller action, and (b) a denormalized `organization_id` on every domain table. Add a third, independent layer: the **`acts_as_tenant` gem**, which auto-scopes *every* ActiveRecord query to a thread-local "current organization" and raises instead of silently returning unscoped data if a query runs with no tenant set. This means even a controller action that *forgets* to apply a Pundit scope still can't leak another organization's rows, because the model layer itself refuses to answer unscoped. `Admin`'s cross-organization visibility doesn't need to be an exception carved into this default-deny posture at all — since `Admin` is a separate account type entirely (§3.0), it simply never runs through `acts_as_tenant`'s `User`-scoped machinery in the first place; its own Platform Console queries are explicit and separately logged (see below), not a bypass flag inside the same code path everyone else goes through.
- **DB-level backstop.** Make `organization_id` `NOT NULL` with a foreign key on every domain table (not just application-level validation) — a stray row with no organization can't exist to be scoped incorrectly. For the Voter Lists table specifically (the most sensitive PII), evaluate Postgres **Row-Level Security (RLS)** policies as an additional DB-enforced layer beyond the three above, given how damaging a voter-data leak would be.
- **`Admin` cross-org access is logged, not just allowed.** Every time an `Admin` views or exports data belonging to a specific organization, write an `ActivityLog` entry (§7a) — who, which organization, what action, when. `Admin`'s broad access is necessary for platform operation, but it should never be invisible, and keeping `Admin` a separate account type (§3.0) makes this easy to enforce centrally in the Platform Console's base controller rather than scattered across org-facing code.
- **Mandatory tenant-isolation tests.** The test suite must include an explicit category of tests whose only job is proving cross-tenant access fails: "a User in Organization A cannot read/update/delete any record belonging to Organization B" (expect 404, not a 403 that confirms the record exists), run for every module, not just spot-checked. Treat a missing test here the same as a missing test for a payment bug — this is a release blocker, not a nice-to-have, and `engineering:review`/`engineering:implement` should check for it explicitly.
- **PII-specific hardening (Voter Lists, §6.7; mobile numbers elsewhere):** field-level encryption at rest via Active Record Encryption (not just transport-layer TLS), export actions logged with who/when/which filters (already in §8), and access to the Voter Lists module itself should be a deliberate, auditable permission grant rather than bundled into general `write` access by default — worth a stricter default than the rest of the module list.
- **Operational basics that matter for data this sensitive:** 2FA (`devise-two-factor`) is **deferred to Phase 2** rather than required for v1 on the `Admin` scope (§2/§3.0) — plan to revisit making it mandatory there once real voter data is live — and recommended for the Org Admin role within `User` when it is added; in the meantime, login rate-limiting (`rack-attack` or similar) and `:lockable` (§2) resist credential-stuffing/brute-force against both scopes, and a security review/pen test pass should happen before this goes live with real voter data — this is worth budgeting as its own pre-launch task, not an afterthought.
- **Legal/compliance note (not legal advice):** handling voter PII and sending political communications is subject to data-protection and election-communication rules that vary by jurisdiction (e.g. India's DPDP Act for personal data, and separate rules around unsolicited bulk messaging — relevant again in §6.6's WhatsApp feature below). Flagging this for an actual legal/compliance review before launch, same as §8 already does for Voter Lists.

## 8b. Scalability & Performance (target: 10,000 concurrent users)

A Rails 8 monolith can comfortably serve 10,000 concurrent users for this kind of workload (mostly CRUD forms, lookups, and dashboards — not high-frequency trading) *if* it's deployed and tuned as a horizontally-scaled system from the start, not as a single server. The main risk isn't the framework, it's a handful of specific bottlenecks that bite Rails apps at this scale if they're not planned for up front:

- **App tier — scale out, not up.** Run Puma in clustered mode (multiple workers × threads per instance) behind a load balancer, with multiple stateless app server instances autoscaled on CPU/request-latency, sized via load testing (see below) rather than guessed.
- **Database connection pooling is the most common failure point at this scale.** Every Puma worker/thread opens its own Postgres connection; with enough instances × workers × threads, the app tier can easily try to open far more connections than Postgres's `max_connections` allows, causing errors under exactly the load you're trying to support. Put **PgBouncer** (transaction pooling mode) in front of Postgres before load testing, not after something breaks in production.
- **Separate databases for Solid Queue / Solid Cache / Solid Cable from the primary app database** (Rails 8 supports this natively via multiple databases). Background-job churn (especially the daily social-media sync fan-out across potentially thousands of pages, §6.5/§6.6) and cache writes shouldn't compete with the primary OLTP workload for the same connections and I/O.
- **Read replica(s)** for heavy-read paths — dashboards (RAG Mapping, Reach Dashboard), Excel exports, Voter List lookups — so reporting load doesn't slow down the write-heavy paths (tickets, cadre activity, ground reports being created by thousands of field users).
- **Cache the hierarchy subtree lookup** (§3.2) — this is the one calculation that runs on nearly every authorized request in the system, so it's the highest-leverage place to optimize.
- **Precompute, don't live-aggregate, the rollup dashboards.** RAG Mapping's color-coded rollups and the Reach Dashboard's trend charts should be computed by a background job into a queryable table (`RagEntry` already has a `computed_at` for this, §7) rather than aggregated from raw tables on every page load.
- **Paginate every table/listing** (`Pagy`) — Voter Lists in particular can run into millions of rows for a full state; "Get All Details" (§5) must mean "all details, paginated," never "attempt to render the whole table at once."
- **Index deliberately:** `organization_id` and `owner_id` on every domain table (already required for correctness in §8a, and just as important for performance), the hierarchy/closure-table columns, and composite indexes on the columns actually filtered on (Voter Lists' state/loksabha/assembly/village, date ranges on reports).
- **CDN in front of Active Storage** for photos/videos/images (CloudFront/Fastly over S3) — don't serve media files through the Rails app itself.
- **Size the background-job workers independently of the web tier**, especially for the social-media sync/bulk-publish fan-out — a large sync batch across thousands of karyakarta pages shouldn't starve time-sensitive jobs like Excel export generation.
- **Observability from day one:** APM (Datadog is already available to this organization) plus Postgres slow-query logging, so a performance regression is caught in staging, not discovered at 10,000 concurrent users in production.
- **Load test before launch, against the real usage shape.** "10,000 concurrent users" supports very different infrastructure depending on what those users are actually doing each second (10,000 idle sessions vs. 10,000 people simultaneously submitting Ground Reports are very different loads) — see §9 #15. Use a tool like k6 or Locust against a staging environment sized like production, simulating the realistic mix (frequent small reads/writes from field users, occasional heavy dashboard/export pulls), rather than assuming the number is met once the infrastructure above is in place.

2. **"RWU" meaning — resolved.** Confirmed as Read/Write/Update. Org Admin (and `Admin`) also has delete rights, but **every delete is a soft delete** (§3.4a) — no domain data is ever hard-deleted.
3. **Hierarchy depth — resolved.** Confirmed unlimited depth; no cap on how many levels the tree can have (§3.2).
4. **Targets module — resolved.** Explicitly out of scope for v1 (§6.9) — skip it entirely until a future phase.
5. **Info / Village-wise Reports** nav tabs — still open. Referenced in the top nav but no screen was provided; needs its own requirements pass before v1 can include them (or they get the same "skip for v1" treatment as Targets — confirm). *(The "Members/Fan Commission" item previously listed here was a misreading of the Mainline/Fan Page Media module label — removed; see §6.10.)*
6. **Multi-organization support — resolved.** SAC-PAD hosts multiple independent organizations (one per Politician, including rival politicians from competing parties — §3.1b), with a platform-level `Admin` above them and org-scoped Org Admin(s) inside each, as described in §3.1.
7. **Data deactivation/offboarding — resolved.** Deactivating an organization (the Politician's account) cascades: every user under it is immediately unable to log in or see any data, at every level of the hierarchy, with no need to touch each row individually (§3.1a). Records themselves are never deleted, just inaccessible while the org is inactive (consistent with soft-delete-only in §3.4a).
8. **One Org Admin per organization, or several? — resolved.** An organization can have multiple Org Admins from day one (§3.1) — no cap of one.
9. **Who can define custom module-scoped roles? — resolved.** Only `Admin` defines roles and their module/capability scope (§3.3). Whoever creates a user (by default, Org Admin only) assigns one of those existing roles to them — Org Admin assigns, it does not define.
10. **Can roles be organization-specific or hierarchy-limited at creation? — resolved (deferred).** Not for v1: there are no self-service custom roles. "Admin" effectively means the development team adding a new role and its scope directly, not an end-user feature. The `roles`/`role_permissions` schema in §3.3 is built to support per-org or hierarchy-scoped roles later without a redesign, but no UI for it ships in v1.
11. **Meta Graph API coverage for Opposition Pages / Comparisons (§6.5) — open, needs a decision.** Automated daily pulls of follower counts, post counts, views, and organic-vs-paid reach are only realistic for pages the organization has been granted admin/Insights access to (its own Official Pages, and cooperating Fan Pages). Meta's API does not expose that level of detail for pages the organization doesn't manage — so Opposition Pages and the Comparisons view cannot get the same automated depth of data. Decide the fallback: manual entry of whatever public numbers are visible, a reduced automated field set (public follower count only, if available), or dropping automated comparisons for those pages entirely for v1.
12. **"Category" for post-reach breakdown (§6.5) — open, needs a definition.** Confirm whether "category" means the post's media format (photo/video/reel/link/text, which the Graph API already labels) or a content-topic tag the team would assign manually (e.g. "rally," "policy announcement," "constituent response") — the second requires a manual tagging UI, not just an API pull.
13. **Connecting hundreds of karyakarta pages (§6.6) — open, affects feasibility.** "One-click post to all pages" only works for pages that already have a valid, connected access token. With potentially hundreds of individually-run pages per organization, who performs each page's Facebook "connect this Page" OAuth step — each karyakarta themselves (self-service connect flow needed), or the Org Admin doing it on their behalf (impractical at scale)? And how are expired/revoked tokens surfaced and re-connected over time without someone noticing a page has silently stopped syncing? This onboarding/maintenance workflow needs its own design before the bulk-posting feature can be considered done.
14. **Bulk WhatsApp/SMS (§6.6) — resolved design, no longer purely deferred.** `BulkMessage`/`BulkMessageTarget` treat WhatsApp and SMS as two channels of one feature, targeted by geography (via `organization.villages`/`organization.assemblies`, §3.1c) or a named `ContactGroup`. Vendor choice (a BSP like Gupshup/Twilio/Interakt, vs. Meta's Cloud API directly) still open and decides the integration work. Before it ships: confirm template-approval content for political outreach, decide how opt-in/consent is handled for numbers sourced from `Voter`, and plan around WhatsApp's tiered volume limits — none of these block the schema, just the actual send.
15. **What does "10,000 concurrent users" actually mean here? — open, needed before infrastructure sizing.** 10,000 people idly logged in, 10,000 simultaneously submitting Ground Reports/tickets, or 10,000 requests/second at peak (e.g. everyone checking the RAG dashboard right after a big event) are very different capacity-planning problems, even though §8b's recommendations (pooling, caching, read replicas, precomputed dashboards) cover all of them reasonably well. Pin down the expected peak usage pattern before load testing, so the test actually validates the number rather than a guess at it.
16. **Which tables get full version history (Tier 1) vs. the lightweight status-change log (Tier 2)? — partially open (§7a).** Confirmed: `Ticket` is Tier 2 (status-change log only). Proposed for Tier 1: `Voter`, `User`, `RolePermission`. Still open: whether `GroundReport`'s resolution workflow and `BulkPostTarget`'s pending/success/failed status should also get the lighter Tier 2 treatment instead of full versioning — not yet decided table-by-table.
17. **Dashboard architecture — resolved.** One shared Organization Dashboard (widget-composed via existing module permissions, plus a few org-admin-only widgets) for Org Admin/User/Dreamline User/custom roles, and a separate Platform Console for `Admin`, since their job is categorically different from running one campaign (§5a).
18. **Admin authentication & naming — resolved.** Modeled as a separate `Admin` account type/table (renamed from an earlier `SuperAdmin` draft to resolve a naming collision — see #19) with its own Devise scope and login route, not a `User` row with a special role (§3.0). 2FA deferred to Phase 2, not required for v1 (§2).
19. **Naming collision between the platform account and the org-level role — resolved.** Both the platform-operator account type (§3.0) and the org-level Politician role (§3.3) wanted the name "Admin." Resolved by renaming the org-level role to `org_admin` (UI label "Org Admin"), freeing up the plain name `Admin` for the platform-operator account type (formerly drafted as `SuperAdmin`). "Organization" itself was also reconsidered as a possible rename to "Client" and confirmed to stay as-is — both the model name and the UI-facing label.
20. **Ops/developer `Admin` tier — partially open.** `Admin.tier` (`full`/`ops`) plus an `admin_organizations` join table lets a developer/support-staff `Admin` be scoped to specific organizations instead of the whole platform, with the Platform Console filtering to just those organizations for an `ops`-tier `Admin` (§3.0). **Still open:** whether `ops` tier gets full admin-equivalent access (including delete) within its assigned organizations, or something more limited such as read-only.
21. **Political Party tracking — resolved.** SAC-PAD targets individual Politicians, not parties, and a Politician can change party affiliation over time without losing history. Added a `parties` reference table (name, abbreviation, color, logo) and a history-preserving `party_memberships` table (§3.1b), with `Organization.current_party_id` as a denormalized fast-lookup pointer to the currently-active affiliation.
22. **Devise module configuration — resolved.** No self-service sign-up on either scope (`:registerable` excluded from both `User` and `Admin`). `:recoverable` ("forgot password") is on the `User` scope only — `Admin` has no self-service password-reset flow by design, so a locked-out platform account is recovered out-of-band (another `Admin`, or direct console/DB access). `:lockable` is on both scopes: `unlock_strategy: :both` for `User` (time-based, or via the existing recovery email) and `:time` only for `Admin` (no email-based unlock, consistent with having no `:recoverable` there). Route paths: `devise_for :users, path: ''` (clean/memorable — the primary, publicly-known login) and `devise_for :admins, path: 'console'` (deliberately non-obvious, so the platform-admin login's existence isn't advertised).
23. **Who manages Kitchen Cabinet ticket categories — resolved.** `TicketCategory` is global reference data managed only by `Admin` — one shared catalog across every organization (same pattern as `Role` and `Party`), while the `Ticket` records filed under each category stay fully org-scoped, unaffected by the category list being shared (§6.1).
24. **`can_create_users` flag vs. hardcoded rule — still open.** Confirmed only `org_admin` creates users under an organization (no change in practice). Not yet decided: whether to keep the `can_create_users` boolean on `Role` as a dormant mechanism for possible future delegation, or remove it entirely and hardcode the check to `org_admin` in policy/model code (§3.3/§3.5).
25. **Cadre Program architecture — resolved.** One shared `CadreActivity` base table + five per-category detail tables (two of the six categories share an identical shape). The category list is a fixed enum, not an Admin-extensible catalog like `TicketCategory` — unlike ticket categories, every Cadre Program category needs its own bespoke columns, so there's no benefit to making the list dynamic (§6.2).
26. **Ground Reports architecture — resolved.** Village-centric: every sub-section (Report, Worship Places, Yatra, Political Position, Local Contacts) is its own table keyed by `village_id` + `organization_id`, since the village is shared geography reference data but the content about it is fully org-scoped — same split as Kitchen Cabinet's categories vs. tickets. Political Position reuses the `Party` catalog (§3.1b) and is history-preserving, like `PartyMembership`. Yatra is a single editable note per village, not a dated event log (§6.3).
27. **Mock Poll — resolved.** Raw Excel upload of village-level survey data, parsed into `MockPollResponse` rows (one per respondent per politician asked about), scoped by village. "Who's likely to win" is computed on read by grouping responses, not a separate tally table (§6.3).
28. **Dreamline User role rename — resolved.** `ad_agency` renamed to `dreamline_user` throughout — same scope and permissions, just the name actually used by the stakeholder (§1/§3.3/§4).
29. **Politician / opponent tracking — resolved.** `Politician` is org-scoped (not global, unlike other catalogs) since one org's opponent roster has no meaning shared with another org's. Managed by `Admin` at onboarding and ongoing, from the Platform Console. Exactly one row per organization has `is_own_politician: true` (partial unique index), kept in sync with `Organization.name` via callback to avoid drift between the two. Used by Mock Poll (§6.3) and Opposition Pages (`SocialPage.politician_id`, §6.5) (§6.3a).
30. **PR module architecture — resolved, simpler than first assumed.** Comparing all six categories' fields side by side showed four of them (Electronic Media, Print Media, Local Print, Local Electronic) are identical in shape and need no detail table at all — just the `PrRecord` base, distinguished by `pr_category_id`. Only Outdoor Media (`PrRecordOutdoorAdCount`, for per-ad-type counts) and Podcasts/Interviews (`PrRecordPodcast`, for a second date) need their own detail table. `MediaPlatform` and `OutdoorAdType` are global Admin-managed catalogs; actual `PrRecord` entries are ordinary org-scoped data under standard Pundit rules. Thumbnail-fetching for Electronic Media is flagged as an open engineering spike, not a schema item (§6.4).
31. **Local Contacts correction — resolved.** An earlier draft wrongly modeled village karyakartas as `User` rows with a `village_id` column — corrected: local karyakartas are not system Users. Replaced with two standalone tables, `VillageLocalKaryakarta` (karyakartas) and `VillageLocalAdminContact` (renamed from `VillageLocalContact`, for non-system administrative contacts like Sarpanch/Gram Sevak/Police) (§6.3/§6.3a).
32. **Geography hierarchy + Organization/constituency link — resolved.** `State`→`Loksabha`→`Assembly`→`Village` are now explicit global, Admin-managed reference tables (previously just a one-line placeholder), reused by `Organization`'s new polymorphic `constituency_id`/`constituency_type` link (§3.1c) to determine which villages/assemblies an org's modules show by default. Fixed for the org's lifetime, not history-preserving like `party_memberships`. Also flagged: the org-scoped village tables (`VillageYatra`, `VillagePoliticalPosition`, etc.) need composite `(village_id, organization_id)` uniqueness constraints, never `village_id` alone, so rival organizations covering the same village never block each other (§6.3b).
33. **Where else does the `Politician`/opponent link apply? — still open.** Confirmed needed for Mock Poll and Opposition Pages (`SocialPage.politician_id`). The stakeholder mentioned "we need opponents in other places too" but hasn't named which other modules — needs an answer before assuming the link is complete everywhere it should be.
34. **`Voter` — flat text or FK into the new geography hierarchy? — partially resolved.** `booth_id` is now a real FK to `Booth` (see #37) — a flat booth number is ambiguous across assemblies/loksabhas, so this one had to be resolved. `state`/`loksabha`/`assembly`/`village` remain flat strings for now, still open, since matching bulk-imported text reliably against the hierarchy tables (§6.3b) may not be clean.
35. **Mainline/Fan Page Media — resolved, deferred to v2.** Confirmed: the entire module (Official/Fan/Opposition Pages tracking, daily Meta Graph API sync, Reach Dashboard) moves to v2, same treatment as Targets. `SocialPage`/`SocialPageMetricSnapshot`/`SocialPagePost` are still built for v1 (they serve Karyakarta Pages, §6.6) — v2 just points them at more page types, no schema change (§6.5).
36. **Social Media module — resolved, several corrections and new designs.** Karyakarta Pages: the karyakarta who owns a page isn't necessarily a system `User`, so `SocialPage` gets the same FK-with-fallback pattern as `VillageLocalKaryakarta` (`karyakarta_user_id`/`karyakarta_name_text`/`karyakarta_mobile_text`); `SocialPagePost` gets explicit `likes_count`/`comments_count` instead of one vague `engagement` field. Influencers gets its own entities (`Influencer`/`InfluencerPost`) since their pages aren't API-connected — only manually-entered "raw data." Paid Promotions and Tag Accounts remain undetailed placeholders. IVRS gets `IvrsCampaign`/`IvrsCallAttempt`, geography-targeted the same way as Bulk WhatsApp/SMS, needing an IVR vendor (Exotel/Knowlarity/Ozonetel-style) as an external dependency (§6.6).
37. **Booth added to the geography hierarchy — resolved.** `Booth` (`village_id`[FK], `number`) extends `State`→`Loksabha`→`Assembly`→`Village` with a fifth level, since booth numbers repeat across different assemblies/loksabhas and the Voter Lists filter/download-by-booth feature needs a real catalog, not a loose number (§6.3b/§6.7).
38. **`Voter` gains `organization_id` — resolved, corrects a gap.** `Voter` was drafted with no tenant-isolation column at all, unlike every other domain table (§3.1) — each organization now bulk-imports and owns its own copy of the roll. This matters because voter sentiment (#39) is inherently org-specific.
39. **Voter sentiment, tied to Kitchen Cabinet resolution — resolved.** `Voter.sentiment_status` (`pleased`/`displeased`/`transit`, mutable — confirmed a voter can move between statuses later, e.g. after a bad experience) is set when a `User` closes a `Ticket` and assigns its `voter_id` (§6.1). Green/Amber/Red is a fixed presentation mapping off the enum, not a stored color. History comes free from `Voter`'s existing Tier 1 PaperTrail versioning (§7a). RAG Mapping (§6.8) gets a new rollup of Pleased/Displeased/Transit counts per village/booth/assembly, answering "how many votes we got."
